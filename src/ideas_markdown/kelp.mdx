**What would Git look like if we designed it today, from scratch, without having to remain compatible with Git?**

That is the question I’m exploring with Kelp.

I want the freedom to reconsider the foundations: what we download, what a commit represents, how independent contributions come together, and how a single repository can use more than one storage machine. At the same time, there is a lot I want to keep: useful diffs, intelligent merging, dependable history, local work, and the ability to recover a known state.

This is an exercise in imagining a successor, with an early working implementation to test the ideas. To make sense of the choices, it helps to first understand what Git was built to do—and why its model has worked so well.

## Why Git exists

Software changes constantly. We need to know what the files looked like before an edit, compare one version with another, recover from mistakes, and combine contributions from people working separately. **Version control** gives that work a recorded history.

Git grew out of a particularly demanding version of this problem: developing the Linux kernel. Contributors were spread across the world, and many lines of development had to proceed in parallel.

The kernel project began using BitKeeper, a proprietary distributed version-control system, in 2002. In 2005, the relationship between its developer and the Linux community broke down and free use was withdrawn. Linus Torvalds began developing Git to meet the project’s needs. The [history in Pro Git](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git) describes the goals: speed, distributed work, strong support for parallel development, and efficient handling of a large project.

So Git was never merely a way for one person to back up a few files. Collaboration and scale were part of the problem from the beginning. Its answer was to let people have their own repositories, work locally, and exchange recorded history.

GitHub and other hosts later made a shared meeting place for that work convenient. Git is the version-control system underneath; a host adds things such as pull requests, discussions, permissions, and build automation.

Now let’s put the machinery aside and picture how the basic idea works.

## Imagine a handbook with many authors

Suppose a team maintains a technical handbook. It has pages about installation, operating services, handling incidents, and deploying releases. Several people edit it, and the team needs to know which advice appeared in each published edition.

Think of a **file as a page**, a **folder as a chapter**, and the **repository as the handbook together with its archive**.

When we make a Git commit, we record an edition of the handbook. The record says which version of every included page belongs in that edition, who recorded it, why, and which earlier edition or editions it follows. The collection of recorded file contents is a **snapshot**.

There is no need to reprint every unchanged page. If the installation page is identical to the one already in the archive, the new edition can refer to that same stored page. Git’s fingerprints of stored contents make that reuse possible.

<HandbookEditions />

Suppose we clarify a page about retrying failed requests. A **diff** shows what changed:

```diff
--- a/operations/retries.md
+++ b/operations/retries.md
@@ -1 +1 @@
-Retry failed requests.
+Retry only transient failures.
```

The minus line was removed; the plus line was added. This tells a reviewer something much more useful than “there is a new edition.”

To record that edit in Git:

```bash
git add operations/retries.md
git commit -m "Clarify which failures should be retried"
```

`git add` selects the contents for the next commit. In our handbook, it puts the chosen revised page on an editor’s tray. `git commit` records the edition assembled from that selection.

This separation is useful: I can include a correction while leaving another unfinished edit on my desk. It also means the draft page, the page on the tray, and the last recorded page can differ. Git calls those the working copy, staging area, and committed version.

That is already a powerful tool: exact editions, explanations for changes, and a way to compare them.

## Take a copy and try a different direction

A normal full clone is like taking home a copy of the handbook and its available archive. I can inspect the history and record new editions without staying connected to a central library.

A **branch** is a movable bookmark in that history. A bookmark called `main` might point to the edition the team works from, while another bookmark follows my unfinished revision. Moving a bookmark is cheap; making a branch does not require physically copying all the pages again.

Two authors can start from the same edition and work independently. One improves the retry guidance, while another corrects the installation instructions. Git can compare both with their common starting edition and usually combine edits to different pages automatically.

That is the basic idea of a **three-way merge**: look at the shared starting point and at what each person changed. If both replace the same sentence with incompatible instructions, the tool asks for a decision instead of guessing.

<HandbookBranches />

We can send our recorded work to another repository with a **push**, and fetch work from it. In practice, teams often gather around a shared host, but the useful local copy remains ours.

I would want to retain all of this in a successor. These are not incidental conveniences. They are why version control makes experimentation and collaboration manageable.

## What happens when the handbook becomes a library?

Now imagine that handbook has grown into many volumes. Different teams maintain different chapters. The archive contains years of revisions and large diagrams. Some readers need the whole collection; others need one page to complete a small task.

A modern codebase can have the same shape: applications, services, shared libraries, generated assets, infrastructure, and documentation kept in one repository. Keeping them together is useful when a change needs to update several parts at once.

But it also exposes questions that are less noticeable in a small project.

**How much do I need to take home?** A developer working on a single service may need only a small part of the repository. A short-lived build environment or coding agent may spend significant time acquiring data before doing a comparatively small amount of work.

Git has real answers here. A **sparse checkout** limits which pages are laid out on the desk. A **partial clone** can leave some stored contents at the library and retrieve them when needed. Those are different choices: which files appear in the working folder, and which contents are stored locally. Git’s [partial-clone design](https://git-scm.com/docs/partial-clone) documents both the benefits and the consequences of needing missing data later.

**Which version did I actually save?** If I put a revised page on the staging tray and then edit it again on my desk, the tray still holds the earlier contents. Tests may run against my latest draft while the next commit records the selected version. Each distinction has a purpose, but it is extra bookkeeping for a person—or an agent—trying to answer a simpler question: what am I about to share?

**How much history needs to be reconciled?** Suppose two authors independently revise different pages and both want to update the shared `main` bookmark. One gets there first. The other cannot simply replace it with their own edition, because that edition doesn’t include the first person’s work.

Git correctly [protects against that update](https://git-scm.com/docs/git-push#_note_about_fast_forwards). The second author can merge, keeping both original commits, or rebase their work onto the newer starting point. Separate branches let both publish independently, with integration happening later. But combining work is still expressed through relationships between project-wide recorded editions.

**Where does the growing library live?** A host can put different repositories on different servers. It can keep several copies of a busy repository to serve more readers. Splitting the storage and write workload of one large repository is a further problem, requiring infrastructure beyond simply placing Git on another machine.

AI makes these questions more immediate. Agents can create many parallel attempts, often in disposable workspaces. Continuous integration repeatedly needs exact source inputs. The cost of preparing a workspace or updating shared state can be paid far more often than an individual developer sees in their terminal.

The point is not that Git cannot support these workflows. It does. The question is which assumptions we would choose if those workflows were central to a fresh design.

## More shelves, more copies, and a lot of coordination

There are two easy-to-confuse forms of distribution in the handbook analogy.

Giving every author an independent copy is like Git’s distributed development model. Operating one library across several buildings is a hosting problem. Solving the first does not automatically solve the second.

A bigger server is a taller bookcase: more capacity, eventually with physical or economic limits. **Horizontal scaling** means adding machines and sharing the storage or work among them.

Extra complete copies can help more people read at once. But those copies need to stay sufficiently current, and somebody still has to determine which updates have been accepted. GitLab’s [Gitaly Cluster documentation](https://docs.gitlab.com/administration/gitaly/praefect/#distributed-reads) describes a case where replicas lag behind a heavily updated repository, leaving the primary to serve most or all of the reads.

There is also maintenance. Git packages and compresses stored objects into **packfiles**. Serving history and keeping those packs efficient involves real computation. GitHub’s [work on monorepo maintenance](https://github.blog/open-source/git/scaling-monorepo-maintenance/) shows how much can be improved by indexing multiple packs and concentrating more maintenance on recent additions.

Recent systems move the durable archive away from the serving machines. Cursor’s [Continuity design](https://cursor.com/blog/git-at-any-scale), published in August 2026, uses a **write-ahead log** in object storage: a durable journal of pushes, with an index governing which entries have been published. Local Git repositories become serving copies that can be rebuilt and brought up to date from that record.

In our library, the journal and archived pages outlive any particular reading room. More reading rooms can be opened without making each one an irreplaceable source of truth. The published log still needs an agreed order, and the stored data still needs maintenance.

GitLab’s [June 2026 scaling proposal](https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/scaling-git/) explores a related separation between authoritative object storage and local caches. Meta’s [Mononoke architecture](https://github.com/facebook/sapling/blob/main/eden/mononoke/docs/2.4-storage-architecture.md) is another important example of separating saved contents from changing records.

This is work I want to learn from. Git compatibility is valuable: existing clients and tools keep working. But maintaining that compatibility also constrains what can change underneath the interface.

Kelp gives me permission to ask a different question: what if the editing model, checkout model, and storage model could all be designed together?

## Start with a blank sheet

For this experiment, I don’t have to preserve Git’s object model or speak its network protocol. I can keep the useful behavior while reconsidering how it is represented.

Returning to the handbook: does every contribution need to be recorded as a new edition of the entire book? Or could the primary record describe the pages being changed and the earlier versions of those pages it replaces?

Imagine an editor submitting a change slip: “replace the retry page I worked from with these revised contents.” Someone correcting `installation.md` can submit another slip. Both refer to the earlier pages they actually used. Neither needs to be rewritten merely because the other slip arrived first.

That is the idea behind a Kelp **commit**. Internally, it is an **edit transaction**: one record containing a batch of file edits. Each edit identifies the preceding version or versions of that path and its new contents, or an explicit deletion. These are file-level relationships; the record is not just the displayed line diff.

With both corrections, the handbook contains the revised retry guidance and the corrected installation instructions. The same two saved edits produce that result whichever arrives first; neither edit needs to be rewritten.

The practical benefit is that I can finish and share my page correction without first integrating an unrelated correction just because it reached the shared host earlier. Work that actually overlaps still needs a decision, as we’ll see in the merging example.

This draws on a long line of work around changes and dependencies, including [Pijul and Darcs](https://pijul.org/manual/why_pijul.html). I’m exploring a particular combination of file-scoped transactions, local workflows, and partitioned storage. I’m not claiming that changes as a primary concept are new.

## Keep related pages in the same envelope

Some edits are independent; others need to travel together.

Suppose the handbook’s installation page refers to a setup script, and we rename that script. Updating only the prose would leave a broken instruction. Updating only the script would leave readers following the old name.

```diff
--- a/docs/installation.md
+++ b/docs/installation.md
@@ -1 +1 @@
-Run ./scripts/setup.sh to prepare the environment.
+Run ./scripts/bootstrap.sh to prepare the environment.
```

The change slip should contain the whole operation: the revised instruction, the old script’s removal, and the new script’s contents. In Kelp, one transaction can record all of those file edits together.

Before the remote publishes that transaction, it checks that the required contents and earlier transactions are available. A reader includes the entire record, not whichever half happened to be easiest to download first.

This also applies to later dependencies. If another edit builds on a file version created by that multi-file transaction, it needs that transaction’s complete logical context.

I can therefore preserve a coordinated change without requiring unrelated pages to acquire dependencies on it. In software, that matters for changes such as updating an API and its callers together.

The tool cannot discover every semantic relationship in the code. Two separate files can still interact badly at runtime. Choosing the right unit of work, reviewing it, and testing the result remain necessary.

## Take home one page, or one chapter

Once work has explicit file-level dependencies, a small checkout becomes a natural part of the model.

In the handbook, I want to take home the retry page and enough history to work on it correctly. I don’t need all the installation diagrams or every unrelated chapter’s changes.

With a Kelp remote configured by its operator, I can select an individual file:

```bash
export KELP_TOKEN="<your access token>"
kelp clone https://code.example.com/handbook \
  --paths operations/retries.md
cd handbook
```

Or I can select several files and directories:

```bash
kelp clone https://code.example.com/handbook \
  --paths operations,scripts \
  --paths .gitignore
```

These are alternative examples using a placeholder server. `--paths` accepts project-relative files and directory prefixes, not glob patterns.

The selected scope is remembered for commits, pulls, and restores. The key rule is that a page absent from my desk is not a page I deleted from the handbook. Files outside the selection are not downloaded or treated as deletions. A file I create outside the selection stays local.

<SelectedPages />

Kelp retrieves relevant transactions and their complete dependencies, along with the historical contents for selected paths. A multi-file transaction retains its full description and original identity even when some of its file contents remain on the remote. Selection changes what is materialized, not what the original author’s commit meant.

If I discover I need another chapter, I can expand the checkout:

```bash
kelp pull --paths docs
kelp pull --paths .          # Expand to the full project.
```

In a software project, the selection must still include what its build and tests require. Kelp cannot infer all those dependencies for me. Nor is a partial checkout a complete backup or a permissions boundary. It is a deliberate choice about which data I need locally.

## Save, inspect, and share deliberately

The ordinary workflow can remain familiar even though the record underneath it is different.

After editing the selected retry page:

```bash
kelp diff
kelp commit -m "Clarify which failures should be retried"
kelp push
```

`diff` lets me inspect the edit. `commit` saves the included file changes locally. `push` shares committed work, leaving later unfinished edits on my machine.

New files within the selected scope are included automatically unless ignore rules exclude them. There is no separate staging tray in this workflow. Saving a version is an explicit decision, and sharing it is another.

I can also start a project locally with `kelp init`, without an account or remote. A failed push leaves committed work queued under its original identity, so retrying doesn’t silently create a new commit from whatever is on my desk at that moment.

Meanwhile, another author can share an edit to the installation page. The remote validates each contribution’s actual dependencies. It does not reject my unrelated page correction because the other person advanced a project-wide bookmark first.

That changes where coordination is needed. We can collect independent contributions while leaving the decision about which combined state to release as a separate concern.

## Keep the useful intelligence in merging

A new model should not make people manually combine changes that a tool can sensibly reconcile.

Suppose the original retry page contains three paragraphs:

```text
Retry failed requests.

Record the request ID in the logs.

Use a fixed delay between attempts.
```

One author clarifies which failures should be retried. Another independently improves the delay guidance. A combined diff would include both edits:

```diff
--- a/operations/retries.md
+++ b/operations/retries.md
@@ -1 +1 @@
-Retry failed requests.
+Retry only transient failures.
@@ -5 +5 @@
-Use a fixed delay between attempts.
+Use exponential backoff between attempts.
```

Both can fit on the same page. Kelp uses the common file ancestor to attempt a three-way text merge, including when there are unfinished local edits to preserve. The original transactions remain available; the combined result is committed explicitly when ready.

Now imagine both authors replace the first paragraph, one with “Retry transient failures” and the other with “Never retry automatically.” That is a disagreement about policy. There is no correct answer hidden in which upload arrived last.

Kelp keeps both alternatives. An existing contributor can choose a starting side, edit it into the intended result, and record the resolution:

```bash
kelp pull --keep-local       # Or --keep-remote.
# Inspect and resolve the competing contents.
kelp commit -m "Resolve the retry policy"
kelp push
```

The side choice changes the working file. The resolution commit records both preceding alternatives as parents, even if the final contents match one of them unchanged. Both original contributions remain inspectable.

This is also a limit of the promise. Competing binary files or a file-versus-directory collision need explicit handling, and an unresolved conflict affecting selected files can prevent a new clone from materializing them. Retaining disagreement is valuable, but the interface still has to help people make the decision.

## Publish an exact edition when you need one

Our handbook still needs editions. A release cannot mean “whatever combination of pages each reader happened to collect.”

Kelp constructs a **view** from a selected set of transactions and all the earlier work they require. In the analogy, this is an edition assembled from a specified collection of change slips. Given the same complete set, clients can derive the same file alternatives.

A conflict-free result identifies exact project contents. A **saved view** records files and their transaction context for recovery. A release tag can give a complete, committed saved view a memorable name.

<PinnedEdition />

From a full checkout of the committed state I want to identify:

```bash
kelp tag v1.0
kelp push
```

The name is immutable: it cannot later be moved to a different view. If separate contributors independently use the same name for different views, both are retained and the exact view identifier is needed to distinguish them.

This does not make a tag an approval or a test result. It gives those processes something exact to refer to. A team’s protected integration policy still needs coordination; Kelp does not claim that merely storing all contributions produces a tested release.

History remains useful at two levels:

```bash
kelp log             # Local saved views and recovery points
kelp log --commits   # Included edit transactions
```

One tells me which states this checkout saved. The other tells me which pieces of work it contains. `kelp show` can inspect either kind using its hash—a fingerprint, normally displayed as a short unambiguous prefix.

To recover the tagged edition:

```bash
kelp restore v1.0
```

Restore first records a labelled backup of the current included files, then restores in place. The output gives the backup’s view hash so I can get back to my previous work. A partial recovery view retains its original scope, even if I expanded the checkout afterwards.

These recovery records are not automatically shared commits. To share a restored result, I deliberately commit and push it. History journaling, inspection, and recovery remain part of the experience rather than being sacrificed to the different collaboration model.

## Put the archive across several buildings

The handbook can now be assembled from independent records while still supporting exact editions. That gives the hosting design different units to work with.

In Kelp’s distributed deployment, **gateways** receive requests, validate contributions, and route them to **storage nodes**. The nodes hold portions of the same project’s contents and journals of its transactions.

Think of several library buildings, each storing part of the archive, with additional copies for resilience. A visitor uses a counter that knows how to find the records. The counter does not need to own the one master bookmark through which every independent correction must pass.

<DistributedArchive />

File contents are stored before the transaction describing their edits is published. The required dependencies and replicated contents are checked, then a complete transaction record makes the whole batch discoverable. Another gateway accepting an unrelated commit does not invalidate it.

Pull combines records discovered from the nodes’ journals and retrieves missing dependencies before constructing a view. Duplicate records identify the same work and do not apply it twice. Journal positions help a client resume transfer; they are not a global ordering of everyone’s contributions.

The result is an exact set of observed work, not a promise that every node was read at the same universal “latest instant.” An immutable view is how I state the particular edition I mean.

The distributed implementation defaults to two durable copies of objects, journal entries, and release pins on distinct storage nodes. With three nodes and two copies, reads and writes can continue with one node unavailable. Too many missing journals cause an error rather than a misleading claim that the absent data doesn’t exist.

Repair and evacuation let operators restore replica placement or move data off a retiring node. Commit identities stay the same when storage placement changes. Gateways need a consistent membership configuration to discover the same nodes.

The goal is for adding machines to help **one project**, rather than only making room for another repository. Physical partitioning and node-failure behavior are implemented and tested. Linear performance scaling is still something to measure, not something I can infer from the diagram. Each node still serializes its own database writes, and validation, discovery, and large views have costs.

## What the clean slate buys—and what it costs

The freedom to choose a new model lets these ideas fit together: take one page or chapter, record edits with narrow dependencies, combine independent work, preserve conflicts, name exact editions, and distribute the stored records.

There are practical file concerns too. Large files use reusable chunks, symlinks retain their targets, and native filenames are preserved on filesystems that can represent them. `kelp gc` compacts physical storage while retaining logical commits, conflicts, saved views, and recovery backups.

But a clean slate is not a free upgrade. Git’s existing ecosystem is an enormous advantage. Kelp has its own format and protocol. Git import can preserve committed history, merge results, modes, symlinks, tags, and original commit information, but that is not the same thing as complete two-way Git compatibility. External LFS contents and submodule projects remain separate concerns.

There are also measured costs. In a [recorded development fixture](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/benchmarks/results/compacted.json) with 1,000 repetitive 4 KiB files and 100 single-file edits, compaction left Kelp slightly smaller than maintained Git: 323,584 versus 330,148 bytes. Kelp’s status and initial capture were slower. The [benchmark notes](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/benchmarks/README.md) explain the workload, persistence differences, and trade-offs. Those development results are not a blanket claim about current-release performance.

The current implementation is 0.0.4. Per-file and directory checkouts, independent transactions, text merging, saved views, large-file chunks, replicated storage, and Git import are working parts of it. There is more to do on very large histories, richer conflict tools, author signatures, finer-grained access control, and review or CI policy around selected views.

The question that matters to me is whether the freedom to redesign those foundations can produce a better overall experience. Can a person—or an agent—work on the part they need, share it predictably, and recover confidently? Can a repository grow across machines while remaining one understandable project?

That is what I mean by reimagining Git today. Start with the job version control needs to do, keep the parts that make it valuable, and give ourselves permission to choose a different shape for the rest.
