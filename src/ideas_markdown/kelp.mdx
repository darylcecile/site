Maya is changing how long checkout waits for a response. Leo is changing the text on its button. They start with the same project, work in different files, and finish independently.

Neither edit needs the other. Why should sharing one make the other person stop and rearrange their work?

That question became the centre of **Kelp**, my exploration of what a successor to Git could look like. It also changed the project substantially. The first experiment was built around automatic checkpoints and repeatedly publishing a named proposal. I’ve since replaced that foundation with deliberate commits that describe independent edits.

The current version is **0.0.4**. Its ordinary commands—`commit`, `push`, `pull`, and `restore`—will look familiar. The more interesting change is what those commands record and how that work can be combined across people and machines.

To explain why I went in this direction, let’s start with the idea Git gets so much mileage from: giving a folder a history.

## First, remember what the files looked like

Our checkout lives in a project folder. One file contains a setting:

```typescript
// checkout.ts
const checkoutTimeoutSeconds = 1;
```

Another contains the button label:

```text
Pay
```

We can edit either file and save it. But saving in an editor replaces the current contents; it doesn’t, by itself, give us an organised project history. If yesterday’s checkout worked and today’s doesn’t, we need a way to inspect what changed and recover an earlier version.

Git lets us choose a set of file contents and record it as a **commit**. Each commit names a **snapshot**: the files as recorded at that point. It also records a message, authorship information, and the earlier commit or commits it follows.

```bash
git add checkout.ts button.txt
git commit -m "Add checkout settings and button copy"
```

`git add` selects the contents for the next commit. `git commit` records that selection. Later we can compare saved snapshots to see what changed.

Git gives stored objects fingerprints calculated from their contents. Unchanged files can be reused across snapshots, so a commit does not mean physically copying the entire project again. Its [data model](https://git-scm.com/docs/gitdatamodel) is a compact, dependable foundation for keeping exact history.

A **branch** is a movable name pointing to a commit. A team might use `main` for its shared line of development. Each developer has a local repository, can commit without an internet connection, and can **push** work to a shared host.

There is a lot here I want to keep: local work, exact saved contents, inspectable changes, and the ability to recover. The question is how much unrelated work needs to be tied together by the history.

## Two files, one shared branch

Maya and Leo both start from our original commit. Maya changes `checkout.ts` to wait three seconds. Leo changes `button.txt` to say “Pay securely.”

```text
Original project
  ├── Maya: checkout waits three seconds
  └── Leo: button says “Pay securely”
```

Suppose they both want to advance the same remote branch. Maya pushes first. When Leo pushes, his commit does not include Maya’s commit in its ancestry. Git normally rejects that **non-fast-forward** update: moving the branch straight to Leo’s commit would stop that branch from including Maya’s work.

That is Git protecting the history, not discovering a textual conflict between the files. The [push rules](https://git-scm.com/docs/git-push#_note_about_fast_forwards) are about the relationship between commits, even when the edits themselves are unrelated.

Leo can fetch and merge, preserving both original commits and creating a commit that joins their histories. Or he can rebase, reapplying his work after Maya’s and producing a new commit identity. Separate branches also let both people publish without competing for the same branch tip. Git has effective ways to handle this.

Still, I wanted to explore a different starting point. What if the record for Leo’s edit said which version of **the button file** it replaced, without making that edit depend on where the whole project’s branch had moved?

This is where Kelp stopped being primarily an experiment in more convenient commands. I needed to change what a commit means underneath them.

## Change what a commit records

The earlier Kelp design gave an ongoing proposal a stable identity and kept its successive revisions together. That helped describe review continuity, but it left me with a larger question about independent work and storage.

I reworked the core around **edit transactions**. A transaction is a batch of file edits recorded together. For each changed file, it says which earlier version or versions it replaces and what the new contents are. Deleting a file is an explicit edit too.

In the interface, making one is still called a commit. Here is the idea in ordinary language, rather than the actual storage format:

```text
Maya’s commit: “Give checkout more time”
  Writes: checkout.ts with a three-second timeout
  Replaces: the original version of checkout.ts

Leo’s commit: “Clarify the payment button”
  Writes: button.txt containing “Pay securely”
  Replaces: the original version of button.txt
```

Both edits depend on the earlier work that created their respective files. Neither depends on the other person’s new edit. An unchanged file adds no edit and no new dependency to the transaction.

Once both commits are available, the combined files are straightforward:

```text
checkout.ts  → Maya’s three-second timeout
button.txt   → Leo’s “Pay securely” label
```

Receiving Maya’s commit first or Leo’s first produces the same result. Neither commit has to be rewritten. There is no extra project-wide merge commit just to stitch those two independent contributions into one sequence.

The implementation builds file state by collecting the recorded alternatives and removing the earlier versions that later edits explicitly replace. The remaining alternatives tell it what is current for each file. Dependencies must be available before that state can be used.

This direction has substantial prior art. [Pijul and the Darcs lineage](https://pijul.org/manual/why_pijul.html) explore changes and their dependencies as primary concepts. I drew on that work while designing Kelp’s file-scoped transaction model. Kelp’s current implementation is not a claim to reproduce all of Pijul’s change algebra or to understand a program’s meaning.

That last boundary matters. Two files can be independent in their recorded edit history and still interact badly when the program runs. Version control cannot infer every API contract between them. We still need tests and review.

## Keep related edits together

Making each file’s history explicit immediately raises another question. What if the work really does belong together?

Suppose I change an API and update its caller in another file. I want to share that pair as one unit. Someone should not discover only the new API half of the commit and mistake that for the intended project state.

That is why a transaction can contain several file edits. It is one record describing the whole batch. Before publishing it, Kelp checks that its required contents and earlier transactions are available.

```text
Commit: “Update the API and its caller”
  ├── new API file
  └── matching caller file

One published transaction includes both edits.
```

If a later edit depends on the API version created by that transaction, it depends on the transaction as a whole, including the caller edit. The implementation does not slice the parent into a convenient half-commit.

This gives me a way to express a relationship deliberately without forcing every unrelated edit in the project into the same chain.

The guarantee is about recorded project state. Replacing several ordinary files on disk is still a sequence of filesystem operations. Local saved views and recovery backups have a separate job protecting that process.

## Bring back deliberate saving

Alongside that change in the model, I changed the ordinary workflow. Saving a version is now deliberate. Sharing it is a separate action.

Here is a complete local starting point with the 0.0.4 CLI installed:

```bash
kelp init shop
cd shop
printf 'const checkoutTimeoutSeconds = 1;\n' > checkout.ts
printf 'Pay\n' > button.txt
kelp diff
kelp commit -m "Add checkout settings and button copy"
```

New files are included automatically unless ignore rules exclude them. `.gitignore` and `.kelpignore` control that inclusion; files already included remain known so their changes and deletions can be recorded. There is no separate staging area in this workflow.

To save an improvement:

```bash
printf 'const checkoutTimeoutSeconds = 3;\n' > checkout.ts
kelp diff
kelp commit -m "Give checkout more time"
```

Editing a file or running `status` does not create a background version. I removed the watcher-based saving model. A commit captures the files intentionally and adds that exact transaction to a local queue of work ready to share.

To share, I configure a project URL and the token provided by the remote’s operator. These values are placeholders:

```bash
export KELP_TOKEN="<your access token>"
kelp remote set https://code.example.com/shop
kelp push
```

`push` sends committed work only. If I have changed the timeout again since committing, that later edit stays on my computer. If the connection fails, retrying sends the same committed transaction with the same identity; it does not silently capture whatever happens to be in the folder now.

This makes the distinction I want visible: the files I’m editing, the commits I’ve chosen to save, and the work I’ve actually shared.

## Share independent work without taking turns

Now Maya and Leo can use the same familiar sequence in separate copies of the project:

```bash
kelp clone https://code.example.com/shop
cd shop
# Edit the files for this task.
kelp commit -m "Describe the edit"
kelp push
```

When Maya edits `checkout.ts` and Leo edits `button.txt`, both can push without first pulling the other person’s commit. The remote validates each transaction’s actual dependencies. It does not ask whether a project-wide branch tip still has the value their work started from.

They use `kelp pull` to obtain each other’s work. Once both know the same commits and dependencies, they construct the same combined view of the files. The original messages and commit identities remain intact.

I made this one of the central [workflow tests](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/apps/cli/tests/workflows.rs): two clients commit separate files, both push, and a third client sees both changes. The test also leaves an unfinished file on one client and checks that it doesn’t appear in a fresh clone.

The intended simplification comes from the dependency model. Renaming commands alone would not produce this behavior.

## When both people change the same thing

Let’s change the example. This time Maya and Leo both edit the original one-second timeout. Maya chooses three seconds; Leo chooses five.

```text
Original timeout: one second
  ├── Maya replaces it with three seconds
  └── Leo replaces it with five seconds
```

Neither edit says it replaces the other. They were made independently from the same earlier file version. Kelp retains both alternatives rather than letting arrival order or a timestamp choose a winner.

Both commits can be stored by the remote. That does not mean the resulting files are conflict-free. **Accepting a contribution for storage and deciding what code to use are different decisions.**

Version 0.0.4 can merge non-overlapping text edits using their common file ancestor. For example, one person changing a timeout near the top of a file and another changing a separate message may combine cleanly. The original transactions are preserved, and the merged result is committed explicitly when ready.

The three-versus-five-second edit overlaps, so Kelp reports the alternatives. An existing contributor can choose a starting side, inspect it, and record a resolution:

```bash
kelp pull --keep-local
# Inspect the chosen files, make any further edits, and test.
kelp commit -m "Resolve the competing timeout edits"
kelp push
```

`--keep-remote` provides the other starting choice. Choosing a side changes the local files; the following commit is what records the resolution. That new transaction names both preceding alternatives, even if its final contents happen to match one of them.

The earlier three-second and five-second commits remain inspectable. Resolving the disagreement adds information about the decision instead of pretending one contribution never existed.

Competing binary contents and structural disagreements—such as one person creating a file where another creates a directory—also need explicit handling. A new clone cannot simply invent a winner for an unresolved conflict affecting the files it needs. This is a real cost of keeping disagreement in the model, and richer conflict browsing is still work ahead.

## Know exactly what you are building

Once commits stop forming one mandatory project-wide line, a commit ID cannot always answer “which complete project should I restore?” Maya’s commit may only describe a change to `checkout.ts`.

I still need exact project states for testing, recovery, and releases. Kelp constructs them from a set of transactions together with all the earlier work those transactions require.

Think of it as choosing “the original shop, Maya’s timeout edit, and Leo’s button edit.” If a chosen commit depends on an earlier multi-file commit, that whole dependency is included too. Kelp gives this selected work a reproducible **view** identity.

A **saved view** records the exact files and their transaction context for recovery. It can also record local draft contents before an operation replaces them. Saving that recovery point does not create another shared commit.

There are consequently two useful histories:

```bash
kelp log             # Saved views and local recovery points
kelp log --commits   # Included edit transactions
```

Each entry has a hash, a fingerprint used to identify the saved object. The CLI normally shows a short, unambiguous prefix. `kelp show` can inspect either kind of entry, while `restore` needs a saved view rather than an independent edit alone.

For a complete, committed project state, a tag gives the view a memorable release name:

```bash
kelp tag v1.0
kelp push
```

Later, I can restore that view by name:

```bash
kelp restore v1.0
```

Restore first saves a labelled backup of the current included files. It restores in place and prints the backup’s view hash, so I have a way back. Ignored files and Kelp’s own metadata remain. To share the restored contents as new work, I commit and push them.

Tags are immutable names for committed, complete saved views. An existing name cannot be moved to a different view. If people independently publish different views under the same name, Kelp preserves both and requires the exact view hash to disambiguate.

A tag supplies an exact reference; it does not itself enforce a review policy or prove a test passed. Review and CI rules can be built around those references. They are not a mandatory approval service sitting in front of every draft push in the current system.

## Work on the part of the project you need

The dependency model also changes what a checkout needs to contain.

Imagine our shop has grown to include an API, mobile apps, reporting tools, and a large asset library. I’m working on the API. I shouldn’t need the asset library’s contents just to change request validation.

In 0.0.3, I added persistent path selections. The selection belongs to the checkout and follows its commits, pulls, and restores:

```bash
kelp clone https://code.example.com/shop \
  --paths services/api \
  --paths .gitignore
cd shop
# Edit files inside services/api.
kelp commit -m "Fix request validation"
kelp push
```

`--paths` selects project-relative files or directory prefixes. These are not glob patterns: `services/api` includes its descendants, but not a sibling named `services/api-old`.

The crucial rule is that a file I did not download is not a file I deleted. Commits compare only the selected paths. A new file created outside that selection stays local instead of accidentally entering the commit.

Version 0.0.4 extends this to the history being transferred. Indexed journals find relevant transactions, and the client obtains their complete dependencies and the historical file contents for selected paths. Unrelated history can remain on the remote.

There is an important qualification to “only my files.” A transaction that changed both the API and its caller still has one identity and one complete description. A partial checkout keeps that transaction’s full meaning even when it doesn’t download the caller’s file contents. Narrowing the checkout must not rewrite the original commit into a different one.

When I need a shared library, I expand the selection:

```bash
kelp pull --paths libs/http
kelp pull --paths .          # Expand to the full project.
```

Draft edits are preserved, with normal conflict handling when a newly selected path collides with local work. Old partial recovery views also keep their scope: restoring an earlier API-only view does not overwrite a library downloaded afterwards.

The selection controls transfer, not permissions. It also doesn’t know all my build dependencies. Root build files, ignore files, and other required code need to be included explicitly. A partial checkout is useful working state, but not automatically a complete backup of the project.

## Split the storage as well as the work

There are two different meanings of “distributed” in this story. Git lets people maintain repositories on their own machines and exchange history. Hosting asks another question: how can several servers share the storage and workload of one large project?

That has become an important part of Kelp’s design. Keeping three full copies of a repository can help serve readers and survive a failure. Splitting a project’s data across storage groups can also increase the capacity available to that same project.

Existing systems already explore this territory. Meta’s [Mononoke architecture](https://github.com/facebook/sapling/blob/main/eden/mononoke/docs/2.4-storage-architecture.md) separates immutable contents from changing records. Cursor’s [Continuity design](https://cursor.com/blog/git-at-any-scale) uses a durable write-ahead log in object storage and replaceable serving copies of Git repositories. A **write-ahead log** records work durably before treating it as complete, helping other copies catch up or recover.

Those approaches show how far Git hosting can evolve. The specific question I’m pursuing is whether independent edits also need to pass through one project-wide write head.

In Kelp’s distributed mode, a **gateway** receives client requests, validates the work, and routes it to storage nodes. The nodes hold portions of the file contents and transaction journals. A journal is a node’s durable record of the transactions it has stored.

```text
Maya’s client → gateway A ─┬─→ storage node A
                          ├─→ storage node B
Leo’s client → gateway B ──┴─→ storage node C

The nodes hold portions of the same project,
with additional copies for resilience.
```

The gateways have no authoritative project-head database. A push brings file contents first, then a transaction describing the whole batch of edits. The gateway verifies the required history and contents before making that transaction discoverable through the relevant journals.

Another gateway accepting an unrelated edit doesn’t invalidate this one. There is no “the project tip must still equal this earlier commit” condition to fail. Overlapping edits are retained as alternatives rather than rejected to preserve one immediately conflict-free branch.

That is the trade-off enabling the different write path. If a team wants every accepted update to advance one globally agreed, tested `main`, that policy still needs coordination. Kelp’s current storage protocol does not quietly promise that stronger model.

## Combine what has arrived without pretending it is everything

Pull asks the storage journals for new transaction IDs and combines their results. Duplicate entries are harmless because they identify the same immutable transaction. A client keeps its place in each journal separately.

Those journal positions are bookkeeping for transfer. They don’t define a universal order in which every person’s work happened.

Before constructing a view, the client retrieves any missing dependencies. If it includes an edit based on earlier work, that earlier work must be accounted for too. This gives an exact, consistent set of observed contributions.

It is not a promise that every journal was read at precisely the same global instant. A later pull may discover more work. An immutable view or release tag is how I specify the particular result I mean.

The distinction also matters during failures. An unavailable node cannot simply be treated as having nothing new. That would make missing data look like a complete answer.

Distributed gateways in 0.0.4 default to two durable copies of each object, transaction journal entry, and release pin on distinct storage nodes. With three nodes and two copies, the implementation supports continued reads and writes while one node is unavailable. A write receipt waits for the required copies; a retry can repair an incompletely replicated attempt.

This is a node-failure property. Putting all the nodes on one machine would not make them independent of that machine failing. Production deployment and failure-domain choices still matter.

I also added replica repair and node evacuation. Evacuation drains a retiring node, copies its data to the remaining members, and can resume after interruption. Adding capacity changes placement and journal discovery without changing the identities of the commits already stored. Gateways need a consistent membership configuration to discover the same nodes.

The [distributed tests](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/apps/cli/tests/distributed.rs) exercise separate HTTP stores and gateways, adding capacity, node loss, and evacuation. Those are concrete checks on partitioning and recovery. They do not establish that doubling the machines doubles production throughput. Each node still serializes its own database writes, and dependency validation and discovery have costs.

## Give large files the same workflow

A project is more than small source files. It may include an image, a model, or another large asset that belongs with the code using it.

The first prototype had a 16 MiB ceiling for regular files. Version 0.0.4 removes that file ceiling by streaming larger files into 4 MiB chunks and recording a bounded tree describing how to assemble them. Unchanged chunks can be reused after an edit.

The user still commits, pushes, pulls, and restores files. Chunking is the storage representation underneath those operations.

The current chunks have fixed sizes. Changing one chunk can reuse the others; inserting bytes near the beginning can shift later boundaries and reduce that reuse. This is useful machinery, but not a promise that every large-file edit becomes a tiny upload.

Symlinks now retain their link targets instead of copying whatever they point at. Native filenames, including non-UTF-8 names on supporting Unix filesystems, are preserved too. A destination filesystem still needs to represent the names and links being checked out; Kelp checks that before replacing files.

There are other bounds. Transaction metadata remains limited to 2 MiB, so removing the per-file size ceiling does not mean one commit can describe an unlimited number of paths. Persistent paged indexes and larger-scale history work remain part of the road ahead.

## See what the design costs in practice

A model can make sense on paper and still produce an unpleasant tool. I wanted measurements that would expose that early.

The [benchmark report](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/benchmarks/README.md) records development runs from the transaction and compaction work. These are earlier fixtures, not fresh measurements of the entire 0.0.4 feature set.

The local fixture contains 1,000 files of 4,096 bytes, followed by 100 one-file commits. It compares Kelp’s commit with Git’s add-and-commit sequence, since both capture the working files. It includes command startup, uses warm filesystem caches, and documents the Git settings. The persistence policies and retained recovery data differ, so the results describe those configurations rather than isolating the engines under identical durability semantics.

Caching the current file state and incrementally updating it made an important difference. Across the recorded before/after runs, median warm status fell from about 198 ms to 16.5 ms, while a one-file commit fell from 163 ms to 30.4 ms. Git in that comparison measured about 13.1 ms for status and 37.9 ms for add plus commit.

That result contains both progress and unfinished work. Git still had the faster status operation. Initial capture was much worse for Kelp: the after-run recorded roughly 27 seconds against about half a second for Git. One initial observation is not a robust performance distribution, but it is a problem to investigate, not a number to omit.

The network fixture exposed another cost: asking for hundreds of small objects one request at a time. In that local fixture, with 5 ms artificially added per request, batching and compression reduced initial push requests from 403 to 7, and elapsed time from about 3.45 seconds to 104 ms. Small updates did not get the same benefit. This was a controlled single-gateway comparison with an earlier Kelp build, not a WAN or multi-node scaling benchmark against Git.

Storage needed attention too. I added `kelp gc` to compact physical storage while retaining every logical commit, saved view, conflict alternative, and recovery backup:

```bash
kelp gc
```

Related objects can be compressed into bounded packs, sometimes representing one object as copy-and-insert instructions against another object within the same pack. Reconstructing the original bytes preserves their hashes. Those storage relationships do not introduce new edit dependencies or require another storage node to decode a pack.

On the recorded repetitive 1,000-file/101-commit fixture, compaction brought Kelp’s storage to **323,584 bytes**, against **330,148 bytes** for maintained Git. That small size advantage belongs to that fixture. After maintenance, Kelp’s status and historical reads remained slower, and compaction added some read cost. Compressed images and other less repetitive data can behave very differently.

What I take from this is a set of engineering directions: avoid replaying all history for ordinary local commands, batch transfers, and measure compression alongside retrieval. None of those removes every cost of directory traversal, large maps, or a busy storage node.

## Bring existing work along

Trying a new system is easier if it can begin with work that already exists. Version 0.0.4 includes Git import:

```bash
kelp import ../existing-git-project shop --ref main
cd shop
```

Import reads the selected revision and its ancestry, preserving committed file states, merge results, modes, symlinks, and reachable tags. Original Git commit bytes and author/committer information are kept as **provenance**: a record of where that work came from.

That matters because a new storage model should not invent a different answer to what an old merge contained. The committed Git result is the thing to preserve, along with its original record.

Import leaves the source repository and unfinished source files alone. Git must be installed for the conversion. External Git LFS contents and the projects behind submodules remain external; importing the Git records alone is not a full copy of those separate stores. A two-way Git bridge is also a different feature from importing history.

The progression through the recent releases reflects the questions I’ve been working through. [0.0.2](https://github.com/darylcecile/kelp/commit/d723d336509dd93ded0c87ababcbb9317a822648) changed the transaction foundation and added the distributed proof and compact storage. [0.0.3](https://github.com/darylcecile/kelp/commit/18ddfb7ac400701a9ba0f088541d1340764f5910) made partial checkout selections persistent and commits safe within them. [0.0.4](https://github.com/darylcecile/kelp/commit/f370c0741bebc4903de76f2cf4f2a0b1d1065f58) expanded the file model, merging, sparse synchronization, replication, import, and release views.

Each step puts another ordinary expectation against the new model: can I work on one folder, recover an earlier state, carry a large file, lose a server, or bring my existing history?

## What I’m trying to prove now

The implementation has moved a long way from the first automatic-checkpoint experiment. The core question is now whether file-scoped dependencies can make independent work easier to share, while still giving people exact states to inspect, test, and release.

The 0.0.4 release records 49 passing local tests, including partial-workspace recovery, text merging, chunked files, Git history import, release pins, and storage-node failures. I still need broader evidence about the experience and its operating limits. The tests are not a substitute for long-running production workloads or usability work with other people.

There are clear gaps: richer conflict resolution for new contributors, efficient handling of much larger maps and histories, cryptographic author identities and signatures, finer-grained access controls, and review or CI policy around chosen views. The present authenticated gateway/storage deployment is not yet a system for untrusted peers to exchange signed work freely.

I also want to know whether the saved-view distinction is understandable in practice. It follows naturally from the model, but “this commit” and “these exact project files” must feel clearer to users, not become new vocabulary they have to fight.

For Maya and Leo, the idea begins somewhere simple: they changed different files, and both should be able to share those changes. Following that question led me to a different commit record, a different synchronization model, and a storage service that can distribute one project’s work. Now the task is to keep testing whether those choices deliver the experience they were meant to support.
