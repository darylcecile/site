The task is to stop a webhook handler from processing the same delivery twice. The fix belongs to one service, but that service lives in a repository containing a dashboard, background jobs, shared libraries, and deployment configuration.

While I work on the handler, someone improves keyboard navigation in the dashboard. An agent updates the installation documentation. A background build wants a reproducible copy of the project so it can run tests.

All of these activities belong to the same codebase. They do not all need the same files, and their edits do not necessarily depend on one another.

That is the kind of workflow I’m thinking about with **Kelp**. I want to keep the benefits of one coherent project while making independent work easier to save, share, and store. The question reaches beyond the command line: what should a commit describe, what should a checkout download, and which decisions actually need agreement between machines?

Kelp is an early implementation of an answer. To explain it, I’ll follow that service fix through the system and the design decisions it requires.

## One task in a larger codebase

Consider a repository organised something like this:

```text
commerce/
  services/
    webhooks/
    exports/
  apps/
    dashboard/
  packages/
    event-types/
  docs/
  package.json
  bun.lock
```

Keeping these components together has practical benefits. A change to an event format can update its producer, its consumers, and its shared types in one piece of work. Tests and releases can refer to a particular state of the whole codebase.

But a small fix doesn’t necessarily need the whole codebase in the working folder. And a documentation edit should not acquire a dependency on my webhook handler merely because both changes happened around the same time.

I want to preserve both kinds of relationship: work that genuinely belongs together, and work that can proceed independently. That starts with how the history describes a change.

## What Git is protecting

Git gives a folder a recorded history. I edit files, select the contents to save, and make a **commit**:

```bash
git add services/webhooks/src/handler.ts \
        services/webhooks/test/redelivery.test.ts
git commit -m "Ignore webhook deliveries already processed"
```

The commit identifies a **snapshot** of the recorded project: which files existed and what their contents were. It also records a message, authorship information, and the earlier commit or commits it follows.

Git does not need a fresh physical copy of every unchanged file to do this. Stored objects are identified by fingerprints of their contents and can be reused across snapshots. Its [data model](https://git-scm.com/docs/gitdatamodel) gives us exact records we can inspect, compare, and recover.

A **branch** is a name pointing to a commit. As work is accepted, the branch moves forward. Developers can keep their own repositories, commit locally, and exchange work with a shared host.

Now suppose my service fix and the documentation change both start from the same commit and are intended for the same shared branch. The documentation change reaches that branch first. My local commit does not include it in its ancestry, even though we edited different files.

Git normally refuses to move the shared branch straight to my commit. Doing so would stop that branch from including the documentation change. This is a **non-fast-forward** rejection: a protection of the recorded history, rather than a report that our file edits conflict.

I can fetch and merge the histories, preserving the original commits. Or I can rebase my work onto the new starting point, creating a replacement commit. Separate branches also let us publish independently and integrate later. These are established, useful workflows; Git does not require every contributor to share one branch.

The question I wanted to explore is whether the underlying record could express the independence directly. My fix replaces particular versions of the handler and its test. Could those edits be shared and combined using just their file relationships, without needing another project-wide history step to join them to the documentation change?

## Give a commit the dependencies it actually needs

In Kelp, a commit records a batch of file edits. Internally, I call this an **edit transaction**. Each edit identifies the earlier version or versions of that file it replaces, together with its new contents or an explicit deletion.

For the service fix, the relationship looks like this:

```text
“Ignore webhook deliveries already processed”
  handler.ts
    replaces the handler version I worked from
  redelivery.test.ts
    replaces the test version I worked from

“Correct the installation instructions”
  docs/installation.md
    replaces the documentation version its author worked from
```

These are descriptions for the example, not literal identifiers stored by the tool. Kelp uses hashes to identify the actual records.

The two commits can share earlier history without depending on one another. Receiving the documentation commit first or the service commit first produces the same file state once both and their dependencies are available. Combining that independent work does not require another project-wide merge commit, and neither original commit is rewritten.

The implementation follows a simple rule: collect the versions written for each path, then remove versions that an included edit explicitly replaces. Whatever remains describes the current file or its unresolved alternatives. Arrival order does not pick a winner.

This draws on ideas explored by [Pijul and Darcs](https://pijul.org/manual/why_pijul.html): changes and their dependencies can be first-class records. My own design uses file-scoped transactions over ordinary saved contents. It does not infer every relationship in the program or reproduce every property of those other systems.

That boundary is important. A handler can depend on a shared event type even if the two files have separate edit histories. Kelp does not discover that semantic relationship by reading the code. Tests and review still have work to do.

## Keep a coordinated change in one piece

Some work really does need to travel together. If I change the event format, I may need to update the producer, the handler, and the shared type declaration in one commit.

That is why a transaction contains a **batch**, rather than making every file an unrelated unit. The whole set of edits lives in one immutable record. Before the remote publishes it, it verifies that the required contents and earlier transactions exist.

```text
Commit: add the delivery identifier to the event format
  ├── producer supplies the identifier
  ├── shared type describes the identifier
  └── handler uses the identifier
```

A reader either includes that transaction or does not. It cannot include the producer half and silently discard the handler half while claiming to have included the commit.

The same rule applies to dependencies. If a later handler fix is based on the handler version from this batch, it depends on the complete earlier transaction. That preserves the relationship its author chose to express.

This gives me two useful properties together: unrelated edits can combine independently, and a deliberately coordinated change remains one unit.

The guarantee concerns the versioned state. Updating several files in an ordinary directory is still a sequence of filesystem operations. Protecting a local checkout during those operations requires recovery records as well.

## Choose the part you need to work on

For the redelivery fix, I need the webhook service and its shared event types. I also need the relevant root configuration. With a project URL and token from the remote’s operator, I can create a selected-path checkout:

```bash
export KELP_TOKEN="<your access token>"
kelp clone https://code.example.com/commerce \
  --paths services/webhooks,packages/event-types \
  --paths package.json,bun.lock,.gitignore
cd commerce
```

The address and repository layout here are illustrative. `--paths` accepts project-relative files and directory prefixes, not glob patterns. A prefix such as `services/webhooks` includes that directory’s descendants, not a similarly named sibling.

The selection is remembered by the checkout. When I edit the handler and its test, the ordinary workflow is:

```bash
kelp diff
kelp commit -m "Ignore webhook deliveries already processed"
kelp push
```

`commit` deliberately records the included files. New files inside the selection are included unless ignored; changes and deletions of already-included files remain known. There is no separate staging area. `push` sends committed work, leaving edits made after the commit on my machine.

For a project that starts entirely locally, `kelp init` provides the same saving model without a server or account. A remote can be configured later. Committing and inspecting work do not require connectivity.

The most important partial-checkout rule is easy to say: **a file I didn’t download is not a file I deleted**. Kelp compares only the selected paths when constructing a commit. A file created outside them stays local.

That rule also has to hold in the history. The client fetches relevant transactions and their full dependencies, but only the historical file contents needed for the selected paths. If a transaction touched the service and a dashboard file, its complete record and identity are retained even when the dashboard’s contents stay remote.

When the investigation reaches another package, I can expand the checkout:

```bash
kelp pull --paths packages/logging
kelp pull --paths .             # Expand to the complete project.
```

Expansion preserves unfinished edits and reports conflicting local contents when necessary. A saved API-only recovery view keeps its original scope even after the checkout grows, so restoring it does not overwrite files fetched later.

This is control over downloading, not an access-permission boundary. It also cannot choose my build dependencies for me. The selection has to include whatever the project’s build and tests need. A partial working copy is not automatically a complete project backup.

## Share a fix while other work continues

The service fix can now be pushed while the documentation work is arriving elsewhere. The remote checks the fix’s real dependencies, rather than comparing its starting point with one project-wide branch tip.

If a connection drops, the local committed record stays available for retry with the same identity. Retrying does not create a new version from whatever happens to be in the working folder at that moment.

I use `kelp pull` to obtain other contributions. Independent edits combine without rewriting either person’s commit. Unfinished local edits are handled separately, so pulling committed work does not implicitly publish my draft.

But real teams eventually overlap. Suppose two people both change the handler’s retry behavior. Both contributions can be recorded, while their resulting file contents may need a decision.

For non-overlapping text edits, Kelp uses the common file ancestor to attempt a three-way merge: compare both versions with the one they started from. The original transactions remain intact, and the merged result is committed explicitly.

When both edits change the same logic incompatibly, no timestamp or arrival order can decide the right implementation. Kelp retains the competing versions. An existing contributor can choose a starting side, inspect the code, make the actual resolution, and test it:

```bash
kelp pull --keep-local
# Resolve the handler and run the relevant tests.
kelp commit -m "Resolve the webhook retry behavior"
kelp push
```

`--keep-remote` selects the other starting side. The flag changes local file contents; the subsequent commit records the decision and names both preceding alternatives. Even choosing one version unchanged acknowledges the competing work. Both original commits remain inspectable afterwards.

Binary alternatives and file/directory collisions also need explicit handling. A new clone cannot materialize an arbitrary winner for an unresolved conflict affecting the selected files. That makes richer conflict browsing an important piece of future interface work.

This is a deliberate trade-off. The remote can retain valid contributions without promising that every combination is immediately conflict-free or ready to release. A team that wants one protected, tested line of accepted work needs a coordinated policy for that decision.

## Name the exact project that passed the tests

Independent commits create an important question for the build system. My webhook commit might describe only two files. Which dashboard, documentation, and shared-library versions belong in the project being tested?

Kelp represents a **view** by a selected set of transactions and all the earlier transactions they require. Given the same complete set, clients can derive the same file alternatives. A conflict-free result supplies an exact set of files to work with.

This is where the distinction between a commit and a project version becomes useful. The commit says what work I contributed. The view says which contributions are included together.

A **saved view** records exact files and their transaction context for local recovery. It may also capture unfinished files before an operation replaces them. That backup is not automatically another shared commit.

The CLI exposes both histories:

```bash
kelp log             # Saved views and recovery points in this checkout
kelp log --commits   # The included edit transactions
```

The entries have hashes, displayed as short unambiguous prefixes. `kelp show` can inspect either kind. Restoring a whole saved state requires a saved-view identifier; one independent file edit alone does not specify the rest of the project.

For a complete, committed state, I can give a saved view a release name:

```bash
kelp tag v1.0
kelp push
```

The tag travels with the project and cannot later be moved onto a different view. If independent contributors create different views with the same name, both are retained and the exact view hash is needed to distinguish them.

I can return to it with:

```bash
kelp restore v1.0
```

Restore saves a labelled backup of my current included files first, restores in place, and reports the backup’s view hash. Ignored files and Kelp metadata remain. If I want to share the restored contents, I commit and push them as new edits; I do not rewind everyone else’s history.

A release tag identifies code. It does not itself certify a test result or approval. Binding those decisions to exact views is the foundation I want review and CI policy to use, but that policy layer is not implemented as a mandatory gate on every push.

## Give the project room to grow

The same repository can become demanding for the machines hosting it. Developers and agents publish changes; build workers request source; file contents and history accumulate.

There are different ways to add capacity. Putting different repositories on different servers helps a host serve more projects. Keeping extra copies of one repository helps with reading and failure recovery. Dividing one project’s contents and independent records across storage nodes addresses another part of the problem.

Git hosting already has substantial engineering in this area. Meta’s [Mononoke storage design](https://github.com/facebook/sapling/blob/main/eden/mononoke/docs/2.4-storage-architecture.md) separates immutable contents from changing records. Cursor’s [Continuity architecture](https://cursor.com/blog/git-at-any-scale) uses a durable write-ahead log in object storage, letting serving copies of Git repositories be rebuilt and scaled independently.

A **write-ahead log** records work durably before treating it as complete. It is useful for recovery and replication. The further question I’m exploring with Kelp is whether unrelated contributions need one project-wide write position at all.

Kelp’s distributed deployment separates gateways from storage nodes:

```text
Developer or agent
        ↓
Any configured gateway
  validates the commit and its dependencies
        ↓
Storage nodes
  hold portions of the project’s contents and transaction journals
  retain additional copies for resilience
```

A gateway routes requests and validates the work. It does not hold an authoritative database of the project’s current head. Each storage node has a **journal**, its durable record of stored transactions.

File contents are uploaded before the transaction is published. The gateway checks the required history and replicated contents; a complete transaction record then makes the entire batch discoverable. An unrelated transaction accepted through another gateway does not invalidate it.

Pull reads the journals, combines the transaction IDs, and fetches any missing dependencies before constructing a view. Duplicate records from replicas identify the same immutable work and do not apply it twice.

This yields an exact set of observed contributions. It does not promise a globally synchronized “latest instant” across all nodes. That is another reason to use an immutable view when specifying what a build or release means.

Distributed gateways default to two durable copies of each object, journal entry, and release pin on distinct storage nodes. With three nodes and two copies, the implementation supports continued reads and writes with one node unavailable. Receipts wait for the required copies. Missing too many journals is an error, not evidence that the missing portion of the project is empty.

Replica repair restores placement, and node evacuation drains a retiring node and copies its records to the remaining members. Adding storage changes placement and discovery without changing existing commit identities. Gateways must use a consistent membership configuration.

This removes a project-wide head from the contribution path. It does not remove every bottleneck: each node still serializes its own database writes, validation can contact dependency owners, and larger views cost more to process. Linear throughput growth and production failure-domain behavior need measurements of their own.

## Fit ordinary project files into that model

The project may include generated assets or other files much larger than source code. I want them to use the same commit, push, pull, and restore workflow.

For regular files larger than 16 MiB, Kelp streams the contents into 4 MiB chunks, with a bounded tree describing how to reconstruct the file. Unchanged chunks can be reused. The current chunk boundaries are fixed, so inserting data near the beginning of a file can shift later boundaries and reduce reuse.

The chunks can be stored independently of the commit that refers to them. This makes large-file contents fit the partitioned storage model, while the transaction still describes one logical file edit.

Symlinks retain their link targets rather than copying the target’s contents. Native filenames are preserved, including non-UTF-8 names on supporting Unix filesystems. A checkout first checks that the destination can represent the requested names and links.

There are still bounds. Transaction metadata is limited to 2 MiB, so a single commit cannot describe an unlimited number of paths. Very large maps and histories need further work on indexing and representation.

Existing Git projects provide another practical test of the model:

```bash
kelp import ../commerce-git commerce-kelp --ref main
```

Import reads the selected committed ancestry, including merge results, file modes, symlinks, and reachable tags. It retains original Git commit bytes and author/committer information as provenance—the record of where the work came from. An old merge result should survive the conversion exactly, rather than be recomputed into different files.

The source repository and its unfinished files stay untouched. Git is required for import. External Git LFS payloads and submodule projects remain external; converting the Git history is not enough to obtain those separate contents. A two-way Git bridge is a further feature beyond this import path.

## Find out where the idea holds up

For this design, a convincing demonstration needs more than two edits combining in a diagram.

I added [workflow tests](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/apps/cli/tests/workflows.rs) where two clients push different-file commits without first pulling, a third client retrieves both, and unfinished local files remain unshared. Other tests retain overlapping alternatives and check that resolving them records both parents.

The [partial-checkout tests](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/apps/cli/tests/partial.rs) check a less visible failure mode: excluded files must remain outside the checkout and must not become accidental deletions. Cross-directory commits keep their original metadata and identity. Recovery is also tested after the selected scope expands.

The [distributed tests](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/apps/cli/tests/distributed.rs) use separate HTTP storage services and databases, multiple gateways, an added storage node, node loss, and evacuation. They establish concrete partitioning and recovery behavior. They do not establish production-scale performance merely because several nodes are involved.

I’ve also recorded [local and network benchmarks](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/benchmarks/README.md). They exposed costs the architecture alone would not tell me: reading many files initially, repeated history processing, small network requests, and storing recovery data alongside transaction history.

Caching current file state and batching transfers helped those workloads. Physical compaction matters too. `kelp gc` groups stored objects into bounded compressed packs while retaining all logical commits, conflicting alternatives, saved views, and recovery backups. The original hashes still identify the same contents.

In the [recorded compaction run](https://github.com/darylcecile/kelp/blob/f370c0741bebc4903de76f2cf4f2a0b1d1065f58/benchmarks/results/compacted.json), the fixture had 1,000 repetitive 4 KiB files followed by 100 single-file commits. After maintenance, Kelp occupied 323,584 bytes and Git 330,148 bytes. But Kelp’s median status took 20.6 ms against Git’s 11.6 ms, and initial capture took about 23.4 seconds against half a second for Git.

Those numbers are from a recorded development build, not a fresh benchmark of the entire current release. The fixture, warm-cache conditions, persistence policies, and retained recovery data matter. The small storage advantage does not cancel out the slower operations, and repetitive text does not predict how compressed assets will behave.

That is the kind of evidence I want to keep alongside the idea: which properties the model demonstrates, which operations have improved, and which costs still make it harder to use.

## What I want the workflow to feel like

For the webhook fix, the desired experience is straightforward. I get the service and dependencies I need. I make an intentional commit. I can share it while unrelated work continues. When there is a real overlap, the competing work stays available. When I need a release or a recovery point, I can identify exact files.

The implementation described here is Kelp 0.0.4. Its release records 49 passing local tests across the transaction model, scoped recovery, text merging, large files, import, tags, and storage failures. It is still an early system.

There is more to do on conflict browsing, much larger maps and histories, cryptographic author identities and signatures, finer-grained access controls, and review or CI policy around selected views. The current authenticated gateway/storage deployment is not an untrusted peer-to-peer exchange system.

I also need to find out how other people understand the workflow. Can they predict what will be committed and shared? Is choosing a saved view for recovery clear? Does working on part of a repository reduce the work they have to think about, or merely move it somewhere less obvious?

The ambition is to let a shared codebase contain many independent streams of work without losing the ability to act on the project as a whole. File-scoped commits, exact views, and partitioned storage are the pieces I’m using to explore that. Their value has to show up in the ordinary work of fixing, testing, sharing, and recovering code.
